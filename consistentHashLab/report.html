01

샤딩 라우터가 만족해야 할 네 가지

키 하나를 노드 하나로 보내는 함수. 그게 전부다. 그런데 실무에서 이 함수에 요구하는 건 네 가지다.

  1. 임의 노드 제거 — 3번 노드가 죽으면 3번만 빠져야 한다
  2. 빠른 조회 — 요청마다 실행되는 코드다
  3. 고른 분포 — 한 노드만 뜨거우면 나머지가 놀아도 소용없다
  4. 최소 재배치 — 노드 1대가 빠질 때 키의 1/N만 움직여야 한다

네 알고리즘을 다 구현해서 재보면, 네 칸을 모두 채우는 행이 없다.

02

인터페이스를 쓰는 순간 결론 하나가 나온다

구현하기 전에 타입부터 적었다.

interface HashRouter {
    fun route(key: String): NodeId
}

/** 노드가 동적으로 들고 나는 토폴로지 */
interface MutableTopology {
    fun add(node: NodeId)
    fun remove(node: NodeId)   // ← 임의 노드 제거
}

Ring · HRW · Maglev는 둘 다 구현한다. Jump는 아래쪽을 구현할 수 없다. Jump의 버킷은 0..n-1이라 끝에서만 늘고 줄기 때문에, 3번 노드가 죽어도 3번을 뺄 방법이 없다.

이걸 UnsupportedOperationException으로 덮지 않고 타입을 갈라서 컴파일 타임에 드러나게 뒀다. 그러자 코드가 §4의 주장을 대신 증명한다 — Jump는 로드밸런서에 못 쓰고 샤드 개수 매핑에만 쓴다. Guava가 consistentHash(long, int)를 하필 이 시그니처로 내놓은 이유이기도 하다. 인자에 노드 목록이 아예 없다.

Jump의 전부 — 이게 알고리즘 하나다

fun jump(key: Long, buckets: Int): Int {
    var k = key; var b = -1L; var j = 0L
    while (j < buckets) {
        b = j
        k = k * 2862933555777941757L + 1
        j = ((b + 1) * ((1L shl 31).toDouble() / ((k ushr 33) + 1).toDouble())).toLong()
    }
    return b.toInt()
}

ushr(부호 없는 시프트)을 shr로 쓰면 컴파일도 되고 대충 돌아가지만 분포가 조용히 망가진다. 테스트가 그걸 잡는다 — 잘못된 버전은 peak/mean이 1.5를 넘고, 정상 버전은 1.05 아래에 머문다.

04

실측

먼저: 잡음 바닥을 모르면 숫자를 읽을 수 없다

키 K개를 노드 N개에 완벽하게 무작위로 뿌려도 노드별 키 수는 다항분포를 따른다. 변동계수(CV)는 1/√(K/N)만큼 흔들린다. 이보다 낮은 CV는 존재할 수 없다.

처음에 peak/mean < 1.05라는 테스트를 짰다가 실패했다. N=1000에서 완벽한 해시도 1.10이 나오기 때문이다. 알고리즘 탓이 아니라 표본의 성질이었다. 이 절이 생긴 이유다.

10001,0003.16 %

링의 CV는 1/√V다 — 모델과 실측이 5% 안에서 맞는다

노드 N개가 각각 V개의 점을 뿌리면 담당 구간은 Beta 분포를 따르고, 여기에 표본 잡음이 직교로 더해진다.

cv ≈ sqrt( (1 - 1/N)/V  +  N/K )
             └ 링 아크의 분산 ┘   └ 표본 잡음 ┘

속도 — HRW만 무너지고 Maglev만 평평하다

예상하지 못한 것 세 가지

  1. 큰 Maglev 테이블은 더 느리다. M=655373은 M=65537보다 65% 느리다(37 ns vs 22 ns). IntArray(655373) = 2.6 MB로 L2 캐시를 넘긴다. 재배치를 줄이려고 M을 키우는 건 공짜가 아니라 조회 지연을 사서 재배치를 줄이는 거래다.
  2. TreeMap 링은 배열 링보다 N=1000에서 4.6배 느리다(663 ns vs 144 ns). 같은 알고리즘, 같은 매핑 결과, 자료구조만 다르다. "안정 해시가 느리다"는 말의 상당 부분은 사실 "TreeMap이 느리다"였다.
  3. N이 작으면 알고리즘 선택이 무의미하다. 키 하나 해싱에 33 ns가 든다. N=100에서 Ring(93 ns)과 Maglev(21 ns)의 차이는 키 해싱 두 번 값이다. 노드 수십 대짜리 시스템에서 이 표를 근거로 알고리즘을 바꾸는 건 최적화가 아니다.

05

가설 채점

측정 전에 적고 커밋한 네 문장. 결과는 3승 1무.

부분 기각
H1 분포

“Jump ≈ Maglev > HRW > Ring”

HRW를 아래로 뒀는데 셋은 구별되지 않았다. Jump·HRW·Maglev 모두 잡음 바닥에 붙는다 (×0.87 ~ ×1.07). 맞은 건 Ring이 뒤처진다는 것, 그리고 그 열세가 1/√V로 정확히 예측된다는 것이다.

확인
H2 재배치

“Ring·HRW는 이론 최소에 붙고, Maglev만 초과분이 생긴다”

맞았다. 다만 초과분의 정체가 예상과 달랐다. 배수는 N에 따라 ×1.02 → ×6.91로 커지지만, 절대 초과분은 0.2~0.6%p에 고정돼 있다. M을 10배 키우면 0.59%p가 0.32%p로 준다.

확인
H3 속도

“Maglev > Jump > Ring > HRW, HRW만 선형 붕괴”

순서까지 맞았다. 다만 N=10에서는 HRW가 1위라는 것, 큰 Maglev 테이블이 캐시 때문에 더 느리다는 것, TreeMap 구현이 4.6배 느리다는 건 예측에 없었다.

확인
H4 운영

“임의 노드 제거 + O(1) 조회 + 좋은 분포를 동시에 갖는 건 Maglev뿐”

맞았고, 그 대가가 H2의 초과 재배치다. §1의 매트릭스가 그대로 답이다.

06

그래서 왜 Envoy는 둘 다 주고, Guava는 Jump인가

여기부터는 기억으로 쓰지 않고 소스를 열어서 확인한 것만 적는다.

Envoy는 트레이드오프를 문서에 적어뒀다

envoyproxy/envoy · api/envoy/config/cluster/v3/cluster.proto
“The table size for Maglev hashing. Maglev aims for “minimal disruption” rather than an absolute guarantee. … Increasing the table size reduces the amount of disruption. The table size must be prime number limited to 5000011. If it is not specified, the default is 65537.”

우리 실험 B가 잰 게 정확히 이 문장의 정량값이다. 같은 파일에서 ring_hash의 minimum_ring_size는 기본 1024, 상한 8M이고, 해시는 XX_HASH가 기본이며, 주석은 그 링을 “ketama ring”이라 부른다.

세션 어피니티가 절대적인 워크로드(장바구니, 로그인 세션)라면 0.6%의 추가 이동이 아프고, 그때는 ring_hash다. 초당 수십만 요청을 라우팅하는데 22 ns와 144 ns의 차이가 아픈 워크로드라면 maglev다. 하나로 통일할 수 없어서 둘 다 있는 것이다.

Guava의 consistentHash는 정말 Jump다

google/guava · com/google/common/hash/Hashing.java
public static int consistentHash(long input, int buckets) {
  long generatorState = input;
  int candidate = 0;
  // Jump from bucket to bucket until we go out of range
  while (true) {
    generatorState = LinearCongruentialGenerator.nextState(generatorState);
    generated = (int) ((candidate + 1) / LinearCongruentialGenerator.toDouble(generatorState));
    if (generated >= 0 && generated < buckets) candidate = generated;
    else return candidate;
  }
}

논문의 루프와 형태는 다르지만 같은 알고리즘이다. 테스트가 랜덤 키 20,000개 × 임의 버킷 수에 대해 비트 단위로 동일함을 확인한다. 그리고 시그니처를 다시 보라 — (long, int). 노드 목록이 없다. 노드를 뺄 방법이 애초에 API에 없다.

ketama의 160 포인트는 어디서 왔나

RJ/ketama · libketama/ketama.c
sprintf( ss, "%s-%d", slist[i].addr, k );
ketama_md5_digest( ss, digest );

/* Use successive 4-bytes from hash as numbers
 * for the points on the circle: */
for( h = 0; h < 4; h++ ) {
    continuum[cont].point = ( digest[3+h*4] << 24 ) | ( digest[2+h*4] << 16 )

    ...
}
/* 40 hashes, 4 numbers per hash = 160 points per server */

서버 이름은 "주소-순번", MD5 다이제스트 하나에서 포인트 4개, 40회 반복. 우리 ketama 호환 모드가 이 규칙을 그대로 옮겼다. 재보니 분포 손해는 10% 이내였다 (N=1000에서 murmur 링 대비 CV +6~10%). 다이제스트 하나에서 뽑은 4개 포인트가 완전히 독립이 아니어서 생기는 차이로 보인다. 호환성 때문에 써야 한다면 걱정할 규모가 아니다. 다만 MD5 키 해싱은 192 ns로 murmur3(33 ns)의 6배다 — 라우팅보다 비싸다.

07

에필로그 — Redis Cluster의 16384 슬롯은 넷 중 아무것도 아니다

Jump의 한계를 우회하는 방법이 하나 있다. 2단으로 나누는 것이다.

key ──(Jump, 고정)──▶ 논리 슬롯 0..S-1 ──(가변 배정표)──▶ 물리 노드

1단은 상태 없는 순수 함수라 절대 안 변한다. 2단은 그냥 배열이라 “3번 노드 빼기”가 자유롭고, 옮길 슬롯을 우리가 직접 고르므로 최소 재배치다. 실측에서도 재배치 ×0.93, 조회 61 ns(N과 무관), 구축 0.1 ms로 거의 모든 칸이 이상적이었다. 공짜 점심인가?

아니다. 분포를 보면 값을 치른 게 보인다.

N (슬롯 S=1024)CVpeak / mean
100.40 %1.005
1004.44 %1.101
100015.23 %2.020

N=1000에 슬롯이 1024개면 어떤 노드는 슬롯 2개, 어떤 노드는 1개를 받는다. 그대로 2배 불균형이다. 슬롯 방식의 균형 한계는 “노드당 슬롯 수”가 정한다. Redis가 16384를 고른 것도 이 산수다 — 1000노드에서 노드당 16슬롯이면 불균형 상한이 6% 수준에 잡힌다.

redis/redis · src/cluster.h
#define CLUSTER_SLOT_MASK_BITS 14
#define CLUSTER_SLOTS (1<<CLUSTER_SLOT_MASK_BITS)  /* 16384 */

/* We have 16384 hash slots. The hash slot of a given key is obtained
 * as the least significant 14 bits of the crc16 of the key. */
if (likely(s == keylen)) return crc16(key,keylen) & 0x3FFF;

그리고 진짜 대가는 숫자로 안 나오는 쪽에 있다. 배정표를 누군가 관리해야 한다. Ring·HRW·Maglev는 멤버십만 알면 모든 노드가 독립적으로 같은 답을 계산한다 — 무상태 합의다. 슬롯 방식은 배정표 자체가 클러스터 전체가 합의해야 하는 상태다. Redis Cluster에 클러스터 버스와 gossip 프로토콜이 있는 이유가 그거다.

안정 해시를 “안 쓰는” 시스템이 아니라, 그 문제를 다른 층위에서 푸는 시스템이다.
해시 함수로 풀면 무상태지만 배치를 제어할 수 없고, 배정표로 풀면 배치를 완전히 제어하지만 그 표를 합의해야 한다.
08

선택 가이드

노드 수십 대, 세션 어피니티가 중요 Ring (V≥160) 알고리즘 차이가 키 해싱 비용에 묻힌다. 검증된 구현이 어디에나 있다.
memcached 클라이언트 호환이 필요 Ketama (160점) 분포 손해는 10% 이내. 대신 MD5 키 해싱 192 ns를 감수한다.
노드 수십 대 이하, 가중치가 자주 바뀜 Rendezvous N=10에서 제일 빠르고, 상태가 없고, 가중치가 자연스럽다.
노드 수백~수천, L4/L7 로드밸런서 Maglev 22 ns 고정. 초과 재배치 0.6%를 감당할 수 있다면.
